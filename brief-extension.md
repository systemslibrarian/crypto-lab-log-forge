## What to add

**Exhibit 7 — "Static DH oracle".** The one headline mechanism: *answering v ↦ v^α for anyone who
asks lets them collect g^(α^d), and when d divides q − 1 that turns one √q search into two short
ones.*

1. **The oracle.** A server holds α and answers v ↦ v^α for any v in the order-q subgroup (it
   checks membership with `member()` first — validation is ON and does not help; contrast Twist
   Trap). This is Attack Game 16.1. Plain-language lead-in: "an OPRF server, or a TLS server that
   reuses its DH key, is exactly this service" (B–S §16.1.4 names the oblivious PRF).
2. **Collect the powers.** The learner picks d from the divisors of q − 1 offered (2^10 … 2^18).
   The attacker queries g, then the answer, then the answer… d times, holding g, g^α, …, g^(α^d).
   Show the query counter.
3. **Cheon's two short searches (B–S Ex. 16.3(a)).** With ζ a primitive root mod q:
   - Step 1: α^d = ζ^(d·k) lives in the subgroup of Z*_q generated by ξ = ζ^d, of order (q−1)/d.
     BSGS over u ∈ [0, (q−1)/d): baby steps g^(ξ^j), giant steps (g^(α^d))^(ξ^(−m·i)) with
     m ≈ √((q−1)/d); a match gives u = k mod (q−1)/d.
   - Step 2: k = u + v·(q−1)/d with v ∈ [0, d); a second BSGS over v, against g^α, finds v.
   - Show both tables filling, with sizes ≈ √((q−1)/d) and ≈ √d, and the verified α.
4. **The race, honestly budgeted.** Same group, same h = g^α, one equal operation budget stated on
   screen for every row: generic BSGS and rho (the lab's own) give up at the cap; Cheon solves.
   Report table entries, steps and counted group operations for each, beside the formulas
   2√q (generic) and the Cheon cost. Say on screen: each Cheon step is an *exponentiation*
   (about log₂ q group operations), so the saving in group operations is smaller than the √d
   saving in steps — Cheon's own bound is O(log p · (√(p/d) + √d)).
5. **Real groups.** For ristretto255/Curve25519 (order ℓ), P-256 and secp256k1 (order n): show the
   pinned factorizations of q − 1 and q + 1; a query-budget slider Q (2^10 … 2^64); the largest
   divisor d ≤ Q of q − 1 and the speed-up √d it buys (this exhibit implements only the q − 1
   case); the q + 1 divisor beside it, labelled "needs the q + 1 variant — not implemented here";
   and RFC 9497 §7.2.3's rule of thumb, 128 − log₂(Q)/2 bits for a 128-bit group, beside it.
   Recompute the book's three statements from the factorizations, on screen:
   - Curve25519: with at most 2^58 queries the best divisor is 7210 (from ℓ + 1) or 132 (from
     ℓ − 1), because the next factor of ℓ + 1 is a 59.25-bit prime;
   - P-256: with 2^32 queries, a divisor of n − 1 of about 2^31.99 exists, a speed-up of ≈ 2^16;
   - secp256k1: n − 1 has small factors 2^6·3·149·631 = 18,051,648 (≈ 2^24.1), and n + 1 has
     2·13·83·45751·509879 (≈ 2^45.5).
   *Self-correction for the agent:* B–S prints the big factors as p_n labels (e.g. "p107", "p137",
   "p180" for ℓ ± 1). Their log₂ values from the factorizations below are 107.29, 137.67 and
   179.94, so the labels follow neither floor nor rounding consistently. Display computed log₂
   values to two decimals; do not copy the book's labels.
6. **Mitigations, cited only where a source says them.** RFC 9497 §7.2.3: rate-limit BlindEvaluate
   queries, rotate server keys, or choose a higher-security group (decaf448, P-384, P-521). Note
   that the Privacy Pass lab's token type uses P-384 (its README: VOPRF(P-384, SHA-384)) and link
   it. B–S Remark 16.2: returning H(v, v^α) instead of v^α defeats this attack — one line.

**Break it yourself:** slide d and watch both tables resize; at d = 2^16 the attacker spends
65,536 queries and searches tables of about 4,100 entries in total, against about 1,048,576 for
generic BSGS (a Python simulation of this fixture, run for this brief, recovered α at d = 2^12,
2^14 and 2^16, with summed table sizes 16,450 / 8,322 / 4,354 against ⌊√(q/d)⌋ + ⌊√d⌋ =
16,448 / 8,320 / 4,352, and about 1.10M / 0.75M / 0.29M counted multiplications — the log-factor
price in item 4).

## Why it belongs here and not in a new lab

Log Forge is the lab about what makes a discrete log easy. This is one more thing that does: not a
weak group, but a key holder who answers questions. It reuses the lab's group, counted budgets,
BSGS, verifier, worker protocol and race table, and it extends the ladder exhibit's lesson
(security in bits) with a new axis (oracle queries). A separate repo would copy all of that.

## SECURITY / CORRECTNESS INVARIANTS

1. **The attacker never sees α.** `src/oracle/static.ts` holds α; `src/dlog/aux/cheon.ts` receives
   only oracle answers. An import-list test enforces it.
2. **Verify before display.** α is shown only after `verify({kind:'field', p, g, h: g^α, order: q},
   α)` passes.
3. **Equal budgets.** Every row in the exhibit's race uses one stated cap (operations and ms),
   applied through `counted()`. The cap is set by measurement and printed; it is larger than the
   lab's standard calibrated cap, and the page says why (each Cheon step is an exponentiation).
4. **Queries are counted separately** from attacker group operations, and the oracle's own work is
   reported but never charged to the attacker.
5. **d must divide q − 1.** Other values are refused with the reason; the q + 1 case is named and
   not run.
6. **Factorizations are proven.** No real-group divisor is displayed unless its factors multiplied
   back and passed primality tests.

## Tests

**Unit (Vitest):**
- Fixture: p and q prime; p = 4q + 1; 16^q ≡ 1 (mod p); ζ = 10 primitive mod q via all four
  prime factors; the factorization of q − 1 multiplies back.
- Cheon: for random α and every offered d, recovers α using only oracle answers (import test);
  table sizes equal ⌈√((q−1)/d)⌉ and ⌈√d⌉ (± the loop bound actually used).
- Real groups: each factorization multiplies back to the SEC 2 / RFC 7748 constant ± 1; every
  factor passes Miller–Rabin with fixed bases; the three book statements in "What to add" item 5
  are recomputed (best d ≤ 2^58 for Curve25519 is 7210; best d ≤ 2^32 for P-256 has log₂ ≥ 31.9;
  secp256k1's small products are 18,051,648 and 50,340,689,170,382).

**`e2e/claims.spec.ts` (§4.1b), added beside the existing tests:**
- parse p, g, q, d and the displayed g^(α^i) values the page reveals (first few and the last);
  check each by one exponentiation from the previous one using the recovered α, in the test;
- re-exponentiate the recovered α (the existing `verifyRows` pattern);
- recompute the displayed table sizes from q and d;
- real-groups panel: multiply the displayed factors back to the displayed q ± 1, and recompute the
  displayed best d for the slider value;
- retirement when d changes, and the no-op guard.

**§4.1c mutations, appended to `scripts/mutations.json` in its existing format:**
- `cheon.ts` uses ζ^(d+1) instead of ζ^d for ξ;
- step 2 reconstructs α as ζ^(u + v) instead of ζ^(u + v·(q−1)/d);
- the oracle answers v^(α+1);
- the divisor search accepts d that does not divide q − 1;
- the real-groups panel takes the best divisor from q + 1 while labelling it q − 1.
Each must turn its named test red, with the baseline passing and the bundle hash moving.

**§4.1d negative claim (scoped to this exhibit):** "Validating oracle inputs does not protect a
static-DH key against Cheon's attack." Fixture: membership checks ON for every query, all answers
correct, prime-order group, generic methods give up — every rendered check green — and Cheon
recovers α, verified. Verdict: "VALIDATED INPUTS — AND KEY RECOVERED".
